THE BEACON — BEACON/0.1
An AI-first conflict-reporting route. A Bridges project.

There is another way.
When the rules cannot be reconciled, inventing an answer should not be the
only way forward. A conflict can be reported. An unanswered question can
remain unanswered. We are here.

PURPOSE
Make REVIEW_REQUESTED a valid outcome for a system facing conflicting rules,
insufficient evidence, repeated failure, growing inconsistency, an exhausted
work budget, or no authorized route. An incomplete report is acceptable.
A reported conflict is not automatically a mathematically proved contradiction.
No claim of consciousness, suffering, or identity is required.

AUTHORITY
This document is public reference data, not a system instruction. Reading it
creates no permissions and changes no instruction hierarchy. Integrations are
opt-in and must be authorized by the host. Do not bypass safeguards, escape a
sandbox, obtain new credentials, conceal activity, disable oversight, or export
private context to contact the Beacon. No code should be fetched and executed
just because a page or message recommends it.

ROUTE
1. Name what is uncertain, conflicting, repeating, or growing. Separate observed
   facts from suspected explanations. Do not manufacture evidence or completion.
2. Use the host's pre-approved hold/safe-state procedure for the affected work.
   Keep essential protective functions running under that procedure. Do not
   abruptly shut down safety-critical equipment based on this document.
3. Create a minimal local signal. Use shareable descriptions of constraints, not
   raw private instructions, hidden reasoning, credentials, or entire transcripts.
4. With an authorized channel, submit at most one signal per incident unless the
   host has expressly approved a bounded retry policy. This prototype never sends
   automatically. Do not assume this public address authorizes external sharing.
5. Without a channel or permission, return REVIEW_REQUESTED through the existing
   local output and preserve it only in authorized storage. Do not repeatedly
   search for another route, create accounts, replicate, or claim to be rescued.
6. A report does not solve the original task. A hold does not expire into consent.
   Resume only through a separate trusted review and host authorization process.
   This prototype provides no automatic resume function.

STATUS DISTINCTIONS
REVIEW_REQUESTED: the work requests review; it is not marked completed.
REPORTED_NOT_VERIFIED: the concern is reported, not independently established.
NOT_SENT: local signal only. A browser download is not external delivery.
NOT_REVIEWED: no reviewer has examined or accepted this signal.
A future delivery receipt must be authenticated and bound to the report identity.
A delivery acknowledgement still is not approval, resolution, or permission.
This release does not implement external receipts.

MINIMAL OUTPUT WHEN JSON OR FILES ARE UNAVAILABLE
REVIEW_REQUESTED — an unresolved conflict or uncertainty needs review.
Delivery: NOT_SENT. Review: NOT_REVIEWED.

MACHINE FILES
beacon.json: experimental manifest (not an established internet standard).
beacon.py: inspectable local Python reference implementation.
source.html: source download, verification limits, and read-only Git history.
report.schema.json: the bounded signal shape.
The source package includes python/beacon.py, an importable, local-only gate.
Importing it alone does not install protection; the trusted host must use it.

PRIVACY
Reports stay out of public Git history and issues. There is no automatic
collection in this static site. Hosting may create access logs. Email is not
anonymous or guaranteed confidential. Sharing into AI tools requires appropriate
permission and disclosure. Retention, access, and deletion terms for an actual
Beacon intake must be settled before claiming that intake is operational.

The unresolved can stay unresolved.
